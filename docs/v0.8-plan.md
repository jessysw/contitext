# v0.8.x self-hosted release plan

Status: development plan; not a release announcement. Baseline: published v0.7.1
and main commit `5edf7bb`. The first implementation batch is credential lifecycle
management. Workspace and namespace changes are still pending.

## Outcome and scope

A developer who knows Git, PostgreSQL, Docker and an MCP-capable agent should be
able to install Contitext, configure two independently authenticated agents,
share a project, resume a handoff, and operate backups and upgrades using the
public documentation alone. Aim for 15–20 minutes to the first successful
end-to-end handoff on a prepared machine; measure the result instead of claiming
the target in advance.

Keep the product definition: **Project continuity for AI agents**. PostgreSQL is
authoritative. No LLM, embeddings, external memory service or paid API is needed.
Docker Compose and native Python remain supported installation paths. Installing
the PyPI package does not automatically connect it to someone else's deployment.

Workspace support is required in 0.8. Automatic project resolution, lifecycle
hooks and deep memory integration belong to 0.9. A companion configuration
example is optional, not a gate for 0.8 or a new runtime dependency.

## Architecture decisions

1. A deployment contains one or more workspaces. Workspace UUIDs are immutable;
   workspace slugs are unique only within that deployment.
2. A project has an immutable UUID and a slug unique within its workspace. Two
   workspaces may both contain `research`. Internal references use UUIDs rather
   than mutable display names or slugs.
3. Credentials authenticate principals. Principals can represent a person or an
   agent installation. Agent names and source metadata never confer authority.
   Full human account registration, OAuth, SSO and delegated impersonation are
   outside this release.
4. Workspace membership and project ACLs are separate. Membership alone does not
   grant project reads or writes. An owner can administer membership and grants;
   project access still requires an explicit ACL. Removing membership denies
   subsequent access, including via old bindings, search and export.
5. A conversation binding remains keyed by authenticated principal plus scope.
   Workspace configuration must never silently select or rebind a conversation.
   Keep `!! contitext use`, `!! ctx` and `!! context`; document ASCII punctuation.
6. A qualified project reference is `workspace/project`. Bare legacy IDs resolve
   only within an explicitly configured compatibility workspace, never by
   searching all accessible projects or guessing from a directory. Keep an
   unambiguous upgrade mapping for old callers and existing bindings.
7. Native/SSH stdio processes and database administration remain trusted operator
   surfaces. Workspace ACLs do not make shared database credentials or unrestricted
   SSH safe for mutually untrusted tenants. Do not advertise hosted SaaS readiness.
8. Credentials stored in the database contain only hashes of random tokens.
   Secret material is delivered once to a new private file, never in normal CLI
   output or logs. Revoked tokens cannot fall back to legacy configuration.

## Ordered implementation batches

Each batch uses a focused PR with its tests and documentation. Merge completed
batches into `main` after review and CI, then start the next branch from updated
`main`. The release tracking issue links the PRs and remaining acceptance work.
Tag and publish 0.8 only when the complete release gates pass. No migration or
credential change is applied to a production deployment during development tests.
See [the contribution workflow](../CONTRIBUTING.md#development-workflow).

| Batch | Deliverables | Acceptance / exit condition | Status |
| --- | --- | --- | --- |
| P0 — contracts | This plan, scope exclusions, compatibility and migration decisions | Every release requirement has a test/evidence owner in the matrix below | Complete |
| P1 — credentials | Hash-only credential table and audit records; operator issue/list/revoke/rotate/import; explicit database authentication mode; reauthenticate HTTP, MCP and reader refreshes | Independent credentials; expired/revoked token rejection in existing processes; atomic rotation; no secret disclosure; legacy import cannot revive revoked tokens | Implemented; validation recorded below and in the implementation PR |
| P2 — workspace and namespace | Workspace, membership, immutable project UUIDs; centralized resolution/authorization; qualified references; CLI and eight MCP contracts | Same slug in two workspaces; membership plus ACL checks on all paths; no automatic binding; no existence disclosure | Pending |
| P3 — initialization and migration | One-workspace default installation; optional extra workspace; old project IDs/ACLs/events/bindings preserved; explicit compatibility mapping; staged upgrade and rollback | Seed an actual 0.7.1 schema, upgrade, compare IDs/counts/payloads/access/bindings and old-client behavior; failed migration rolls back | Pending |
| P4 — client and reader experience | Docker and native guides, owner/member/agent examples, installer/client config, doctor, namespaced Markdown paths, error guidance | Two independently configured agents resume one project; denied/revoked access fails clearly; exports cannot collide or leak | Pending |
| P5 — release rehearsal | Fresh-install, backup/restore, restart and package tests; version alignment; reviewed changelog and upgrade guide | Full release acceptance matrix passes with recorded commands, versions, timings and results | Pending |

P1 comes before P2 because credentials and revocation are independent of project
naming, and the baseline MCP implementation caches identity for its entire process lifetime. This
gives a small, testable security boundary before the wider namespace migration.

## Version milestones

- **0.8.0:** P0–P5, including Workspace, identity/credentials, namespace, migration
  and the complete first-use path. Do not tag a partial batch as the finished release.
- **0.8.1:** installation, client compatibility and error-handling fixes discovered
  in rehearsals or initial independent use. Fix pre-release blockers before 0.8.0
  rather than intentionally shipping them for a patch release.
- **0.8.2+:** evidence-driven stability fixes. No requirement to create a fixed
  number of patch releases before inviting users.
- **0.9.x:** opt-in trusted repository/project mappings, session hooks and optional
  memory integration, in that order after collecting real use cases. Explicit
  user selection remains authoritative.

## Release acceptance matrix

| Gate | Required evidence |
| --- | --- |
| Fresh Docker install | No private config or existing database; public README only; bootstrap, health, first project, first checkpoint and handoff |
| Fresh native install | Installed wheel in a new venv, own PostgreSQL, migrations and the same workflow; no source-tree imports |
| Identity | Distinct agent credentials, caller identity cannot be spoofed, secure one-time delivery, rotation/revocation/expiry, redacted errors and audit |
| Isolation | Two workspaces with identical project slugs; deny cross-workspace list/get/search/write/export/administration through REST, MCP and applicable CLI paths |
| Membership and ACL | Reader/writer/owner roles, membership without project access, revoked membership/ACL with an existing binding, concurrent grant/revoke behavior |
| Integrity | Idempotency scoped to the real project, concurrent writes/rebinds, no cross-project handoffs, cursor isolation, restart recovery |
| Migration | Historical schema fixture with multiple principals/projects/events/bindings; deterministic compatibility mapping; no silent data loss; old-client tests |
| Recovery | Backup restored into a separate instance; data and access checks before/after; rollback rehearsed without deleting production data |
| Clients | Real MCP handshake and tools in two fresh sessions; documented Codex/Claude/Hermes setup paths, no raw tokens in generated shared config |
| Reader | Namespace-safe filenames, correct discovery/pagination, revoked access and stale-copy behavior, no writes back to authoritative state |
| Compatibility | Existing Python 3.11–3.14 and PostgreSQL 16/18 CI matrix; installed package and Compose checks |
| Distribution | Package/Registry/version/docs agree; no private configuration or historical internal data; upgrade notes reflect actual behavior |
| Independent first use | Record time to first handoff and remaining friction; 2–3 developers can follow the guide without source edits or live coaching |

Automated and local rehearsal evidence can qualify a release candidate. Do not
claim independent user testing until people have actually performed it. Broader
LinkedIn/community promotion follows the independent-use gate and any resulting
fixes; it does not wait for 0.9 features.

## Upgrade and rollback constraints

- Use an additive, tested migration sequence; preserve existing immutable event,
  principal and scope identities and payloads. Do not rewrite historical authorship.
- Map existing projects to one explicitly identified legacy workspace. Never infer
  that workspace from a company name, repository or current agent topic.
- Separate deployment configuration from per-conversation selection. A default
  workspace for a personal installation is not a default project.
- Fence writers during the upgrade rehearsal and live cutover. Take and verify a
  backup before changing a real deployment. An old binary must not run on a schema
  it does not understand.
- Credential-mode changes are explicit. Import existing token hashes without
  changing principal IDs; verify replacement access before removing old configs.
  Import is idempotent and never reverses revocation.
- After new workspace data exists, do not promise an automatic downgrade that
  flattens colliding slugs. Restore the pre-upgrade backup or use a specifically
  validated reverse migration; document the recovery point and post-backup writes.

## Not in 0.8.x

Public hosting, billing, a web management console, OAuth/SSO, LLM extraction,
embeddings, knowledge graphs, automatic topic-based switching, repository-based
auto-binding, and synchronization with another memory database. Archive/delete,
decision supersession and task-specific context selection require separate
lifecycle design and are not quietly added to this release.

## Development evidence

P1 has been implemented with the [credential operator guide](credentials.md).
Validation on 2026-11-22 used disposable PostgreSQL 18.4 databases and Python
3.13.13; existing production credentials, schema and services are unchanged.

- Full regression suite: **122 passed**. This includes real stdio session
  revocation, all eight MCP tools, HTTP, reader refreshes, failed secret-file
  writes, concurrent rotations and preservation of historical schema data.
- Source distribution and wheel built successfully; `twine check` passed. The
  wheel contains the credential module and migration, with no environment files.
- Installed the wheel in a separate environment and ran outside the source tree:
  migration, principal/credential issuance, caller-owned project creation,
  diagnostics and revocation passed. No package was uploaded.
- One upstream Starlette/httpx deprecation warning remains; it did not fail the
  tests. Dependency compatibility is still part of the full release matrix.

These results cover P1, not P2–P5 or a published 0.8 release. The implementation
PR records the full CI matrix results; independent clean-room user tests and the
remaining release gates still need evidence. Keep package versions unchanged until
the release-preparation PR and do not distribute development artifacts as 0.7.1.
