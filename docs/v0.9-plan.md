# Contitext 0.9 Core development plan

Status: proposed, awaiting maintainer review. Documentation changes do not
authorize feature implementation, publication, or deployment.

Baseline: v0.8.4 (`07ed6abc12fcf64b12e60f2cdc5d0a230dd4dc76`).
Reviewed: 2026-11-26.

## Objective

Make the open-source Core suitable for authenticated remote MCP use by
self-hosters and hosting operators. Retain the complete CLI, local MCP,
authorization, project continuity and agent integration capabilities.

Version 0.9 adds hosting support to the Core product. It does not announce an
operated hosting service. A consumer can deploy the released Core package or
image without a product-specific control panel, account system or external
service dependency.

The [hosting integration contract](hosting-integration-contract.md) describes
the provider-neutral boundary. It is a proposed interface contract, not an
assertion that these capabilities are implemented in 0.8.4.

## Verified starting point

| Area | Existing capability | Core work required |
| --- | --- | --- |
| MCP | Eight tools over stdio, with a process-selected credential | Streamable HTTP and request-scoped identity |
| REST | Bearer authentication and a shared application service | Consistent remote authentication and resource limits |
| Isolation | Workspace UUIDs, membership plus project ACLs, principal-scoped bindings | Credential restrictions and remote multi-user isolation evidence |
| Credentials | Hash storage, expiry, rotation, revocation and lifecycle audit | External-subject mapping and bounded remote grants |
| Clients | Native/SSH stdio; eight agent integration surfaces | Remote profiles, transport, authentication references and optional bridge |
| Reading | Authenticated Markdown export and optional Obsidian workflow | Bounded remote reading and complete portable export |
| Distribution | PyPI, MCP Registry, Homebrew, source-build Docker | Tested public OCI images and consistent artifact publication |

Source anchors: `src/contitext/mcp_server.py`, `auth.py`, `credentials.py`,
`namespaces.py`, `repository.py`, `resolution.py`, `session_client.py`,
`hook_transport.py`, `models.py`, `compose.yaml` and
`.github/workflows/publish.yml`.

The connection loader currently accepts only `command`/`args`; session and hook
clients launch stdio subprocesses. Adding a URL field alone cannot enable remote
automation. The compatibility workspace is process-wide, so it cannot select a
different personal workspace for every user of a shared process. Existing
self-hosting ACL tests are a starting point, not proof of public-tenant readiness.

## C0: design and compatibility gate

Before feature implementation, record the request identity/grant model,
operator API boundary, threat model, protocol/SDK baseline and client matrix.
Review whether additional database isolation, including RLS, is necessary;
resolve identified isolation gaps before accepting untrusted remote callers.
Do not claim that PostgreSQL RLS already exists.

Core acts as an OAuth resource server and integrates with an existing
authorization server. Verify discovery, PKCE, access-token audience and client
registration behavior against a reference implementation. Social login alone is
not proof of MCP authorization compatibility. Provider-specific registration,
account pages, deployment configuration and commercial policy are not Core work.

The current official MCP specification is revision 2026-07-28, which changes
Streamable HTTP session behavior and favors Client ID Metadata Documents while
retaining legacy DCR compatibility. The current package uses `mcp>=1.30,<2.0`.
Test the actual SDK/client combinations before choosing implementation APIs or
changing that dependency range. Protocol compatibility must be stated explicitly.

## Core design boundaries

### Identity, grants and project state

- Preserve principal/workspace/project UUIDs, event provenance and existing
  membership-plus-project-ACL semantics. Workspace ownership does not imply
  permission to read every project.
- Map a verified `(issuer, subject)` to a stable principal. Display names,
  email addresses, tool arguments and caller-supplied identity headers are not
  authentication. Do not merge accounts automatically by email.
- Resolve identity for each HTTP request and tool invocation. Use request-local
  authorization context, never a mutable process-global principal or shared
  server credential. Effective access is the intersection of grant restrictions,
  workspace membership and project ACLs.
- Add generic workspace/operation restrictions for remote credentials and
  external grants without silently changing existing self-hosted credentials.
  Unknown and unauthorized project results remain non-enumerating.
- Require qualified `workspace/project` references in shared remote deployments.
  Keep the legacy compatibility setting opt-in for existing installations; never
  choose a tenant from a repository name or a process-global personal default.
- Keep conversation bindings independent of transport connections. Reconnect and
  token rotation preserve stable principal/scope identity and cannot silently
  select another project. Mapping/outbox identity must not depend on a rotating
  secret. Explicit selection and existing authorized bindings remain authoritative.

### Remote MCP resource server

Reuse the official SDK, shared application service and existing eight MCP tools.
Keep stdio, REST, tool names/parameters and binding semantics compatible.
Remote transport is explicitly enabled, with documented secure deployment
settings; installation must not start a service or expose a public listener.

Validate issuer, audience/resource, signature or introspection result, expiry and
grant restrictions. Supply protected-resource metadata and appropriate
authentication challenges. Support scoped expiring credentials where needed for
noninteractive clients without requiring a particular hosted provider.

Database-key revocation continues to affect subsequent authenticated calls.
External-grant revocation and suspension require an authoritative check and a
tested propagation bound. JWT signature validation alone does not prove that a
grant is still active. Verifier failures fail closed.

Provide Origin/host validation, trusted proxy configuration, bounded request
handling, deadlines and safe authorization metadata fetching. Test legacy
transport sessions where supported without confusing them with persistent
application `scope_id` and `session_id` values.

### Generic operator interface

Provide a versioned Python interface over Core-owned transactions for external
identity mapping, workspace/owner provisioning, scoped credential management,
suspension, portable export and explicit workspace purge. Exact typed symbols
and transaction semantics are frozen in C1/C4 and documented with package tests.

This is a trusted operator surface, not a new set of MCP tools or an unrestricted
public admin API. Operators protect database credentials and enforce the
documented actor/ownership requirements. Ordinary user data operations retain
Core authorization; an operator credential is not a substitute for user ACLs.
Keep runtime and provisioning database roles distinct and non-superuser where
their operations permit it. Core owns all migrations of Core tables.

### Remote clients, hooks and plugins

Extend one shared connection/transport abstraction and reuse it in configuration
generation, diagnostics, plugins, hooks and an optional stdio-to-HTTP bridge.
Use private credential references, not secrets in URLs, arguments or shared
configuration. Preserve existing stdio profiles and stable Homebrew paths.

Record actual versions and connection modes for Codex, Claude Code, GitHub
Copilot, Cursor, OpenCode, Gemini CLI, Hermes and OpenClaw. A native host's OAuth
cache is not assumed readable by independent hooks. Hooks need their own
authorized credential or an explicitly supported credential broker.

Basic native remote MCP use should not require a local Contitext server.
Automatic context loading and checkpoints remain opt-in local integrations with
normal client trust requirements. Preserve bounded startup, nonblocking failure,
idempotency, binding conflict checks and durable outboxes. Bound transient
retries; permanent authorization failures must not replay across accounts or
loop indefinitely.

### Limits, export and lifecycle

Core implements generic policy enforcement and usage/audit signals. Operators
configure policy values. Bound project/storage growth, request/response sizes,
rate, concurrency, connection pools and query time. A second credential must not
bypass a workspace limit; idempotent retries must not double-count committed data.
Enforcement must hold across multiple processes.

Use bounded context assembly for interactive reads. Handle oversized legacy
responses explicitly rather than silently truncating authoritative records.
Offer complete versioned portable export separately from display-only Markdown.
Exports apply the documented caller ACLs and contain no credentials. Do not expose
a shared filesystem projection across tenants.

Separate suspension from deliberate deletion. Define purge ownership checks,
concurrent-write fencing, binding/reference cleanup and preservation of other
workspaces. Purge is an explicit operator capability, not a new chat command.
Expose lifecycle outcomes that operators can reconcile with retained backups.
Audit actor/operation/target/outcome without logging raw context or secrets by
default.

### Distribution and upgrade

Publish public OCI images for linux/amd64 and linux/arm64 from the verified
release wheel. Record digests, provenance and SBOM; scan and functionally test
the artifacts. Keep source-build Docker, Python and Homebrew paths available.

Ship a provider-neutral remote self-hosting example and migration/restore guide.
Retain Python 3.11-3.14 and PostgreSQL 16/18 coverage. Controlled migrations must
not race across replicas; image rollback does not imply a safe schema downgrade.
Do not migrate a user's working deployment as a release side effect.

## Delivery units

After plan approval, use five focused implementation PRs and one release PR.
Each PR includes tests and relevant documentation and is squash-merged only when
its own acceptance is complete. These are review units, not six patch releases.

| Unit | Complete deliverable | Dependency and acceptance |
| --- | --- | --- |
| C1 | Request identity/grants, external subjects, additive migration, operator provisioning interface | C0; legacy upgrade, idempotent provisioning and concurrent isolation pass |
| C2 | Streamable HTTP, OAuth resource validation/discovery, scoped credential access | C1; real network authentication, expiry, revocation and transport tests |
| C3 | Remote profiles/configuration, bridge and hook/plugin transport | C2; eight adapter contracts and preserved stdio/offline behavior |
| C4 | Resource limits, audit/usage signals, portable export, suspension/purge | C1/C2; concurrent quotas and cross-tenant lifecycle tests |
| C5 | OCI build/publication pipeline and remote self-hosting/upgrade documentation | C2-C4; clean image install, migration and functional MCP smoke |
| R1 | Version alignment, acceptance report, 0.9.0 release and distribution verification | All Core gates below; unchanged tested artifacts are promoted |

Keep current stable installation instructions on 0.8.4 during development and
label new functionality Unreleased. Test immutable candidate artifacts in
isolated environments; no public RC/beta version sequence is required. Publish
0.9.0 once its gates pass, then verify the published package/image. Later patch
versions follow fixes and evidence, not a preset feature-per-patch schedule.

## Core release acceptance

1. Existing regression, stdio/REST, Python/PostgreSQL, Homebrew and hook behavior
   pass. Rehearse upgrade from 0.8.4 without losing principal/event identities.
2. Distinct principals reuse project slugs, scope/task IDs, cursors and
   idempotency keys under concurrency. List/read/search/write/bind/export and
   operator paths cannot cross their authorization boundaries or disclose names.
3. Missing/invalid/expired/wrong-audience tokens, spoofed identity fields,
   revocation, suspension and verifier outages fail correctly. Discovery,
   refresh, reconnect and supported registration modes work in real requests.
4. Exercise eight remote adapter paths automatically. At least two actual host
   applications, initially targeting Codex and Claude Code, complete remote
   project creation/selection and cross-agent handoff. Separate fixture/SDK tests
   from real-host evidence; claim only verified remote modes and versions.
5. Hook deadlines, checkpoint/handoff, interrupted network, restart/outbox replay
   and credential rotation preserve binding and account isolation.
6. Enforced quotas and bounded queries survive concurrency and extra credentials.
   A noisy caller does not make unrelated authorized callers unusable. Document
   benchmark conditions; do not imply an operated service SLA.
7. Export and purge preserve authorization and unrelated workspaces. Restore a
   backup into an isolated deployment and verify events, memberships and bindings.
8. No private configuration, credentials or operational customer data appear in
   public artifacts, diagnostics or normal logs. Runtime/operator surfaces and
   database networking are secure by default in the documented examples.
9. README, tag, GitHub Release, PyPI, Registry, Homebrew and OCI references align.
   The published image/package pass a clean remote MCP write/read smoke.

## Out of scope

Account-registration sites, user dashboards, provider-specific hosting plans,
commercial policy, infrastructure operation and customer onboarding are consumer
responsibilities. They are not Core milestones or prerequisites for releasing
Core once its independent acceptance passes.

General-purpose memory/RAG, semantic project guessing, hosted agent execution,
repo cloning, filesystem access, unrelated refactoring and private deployment
migration are also outside this milestone. Preserve the `contitext:` command
syntax and explicit binding authority.
